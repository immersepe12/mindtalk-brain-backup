## 4. 🔴 ROOT CAUSE FOUND — T5 weekly brief cap silently halved (`N/10` instead of `N/20`)

**Kushal asked:** are 20 pages/week publishing automatically? **Answer: no — 4-8/week.** Investigated to root cause.

### The bug
`config.json → thresholds.max_new_content_per_week = 20` (correct). But T5 has been **writing and
enforcing a denominator of 10** in its weekly logs:

| Week log | Reported | Should be |
|---|---|---|
| briefs-2026-07-06 | `0/10` | 0/20 |
| briefs-2026-07-20 | `2/10` | 2/20 |
| briefs-2026-07-21 | **`10/10`** ← stopped, believing it was at cap | 10/20 (10 slots unused) |
| briefs-2026-07-27 | **`9/10` "1 slot remaining"** | 9/20 — **11** slots free + FLOOR MISS (9 < 12) |
| briefs-2026-07-13 | `6/20` ✅ | (the one correct week) |

**Two compounding effects:**
1. **Cap halved** — T5 stops generating at ~10 briefs/week instead of 20.
2. **Floor misses masked** — 9 against a floor of 12 should raise `⚠️ BRIEF FLOOR MISS`. As `9/10`
   it reads as "nearly full", so the alarm never fired.

**Downstream:** brief queue starves → T9 has nothing eligible (2026-07-29: 8 scanned, 0 shippable) →
published output stuck at **4-8/week vs 20/week target** → contributes directly to the largest open
gap, **impressions −23.5% vs 420K Q3 target**. Surface area is the binding constraint and this bug
was capping it.

**This is a REGRESSION.** A `N/5` version of the same bug was fixed 2026-07-20; it returned as `N/10`
and ran 4 more weeks. The old guard was a *negative* instruction ("NEVER write N/5") — too weak.

   `config.json` at runtime, never memorised**; literal required output format
   `Weekly total: N/20 cap (floor: 12)`; `remaining = 20 - N` computed not assumed; explicit
   regression history so the next agent recognises the failure mode.
